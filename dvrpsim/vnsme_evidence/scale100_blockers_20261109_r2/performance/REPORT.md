The unchanged Java source explains the scaling and stopping risks:

- `main_algorithm.java:106` starts `System.nanoTime` before reading/restoring/dispatching. The 540-second checks in `variableNeighbourhoodSearch` (235-260 and 276-281) are cooperative checks between calls, not an interrupting deadline. `blockExchange` (814-1020), `blockRelocate` (695-812), and `interCoupleExchange` (1022 onward) contain no inner deadline check. Successful exchange/relocate branches execute `continue`, so some subsequent checks are skipped. The next loop starts with `interCoupleExchange` before checking time. Long initialization, a long neighborhood call, repeated successful first-neighborhood calls, and final cost/publication can therefore extend beyond 540 seconds. This is a demonstrated lack of a strict internal bound; it is not proof that this mechanism caused epoch 127.
- `blockExchange` constructs movable supernodes, then enumerates unordered pairs of B blocks: up to B(B-1)/2 pairs per call. Each trial mutates/copies `ArrayList` route segments, checks capacity/LIFO feasibility, computes a cost, and restores the routes. `blockRelocate` tests each block across vehicle insertion positions, approximately B times the total number of route positions per pass. `interCoupleExchange` repeats pair enumeration as well. All these passes restart after successful moves.
- `cost(ArrayList<Node>, Vehicle)` (3593-3871) first checks route feasibility, then constructs fresh arrays and a dock table and replays all vehicle routes. It is not a local cost delta for the supplied vehicle. For N route nodes and K vehicles, the event-selection scan alone is proportional to K times the number of scheduled events, with additional item processing, dock-slot scans/removals/sorts, string key construction, `split`, and numeric parsing. Feasibility uses insertion/removal at the front of an `ArrayList` (4091 onward), so item-stack operations can themselves become quadratic in the number of items. Cost is evaluated repeatedly for overlapping candidate states; there is no memoization or incremental schedule reuse in these methods.
- Search behavior can permit repeated deterioration/re-improvement: `improveCIPathBy2Opt` accepts `minCostDelta < cost0 + addDelta` (412), with `addDelta=300000.0` (96). This allows moves above the starting objective. `blockExchange` initializes `minCost=originCost` but does not update that threshold when recording an improving candidate (920 onward, 961 onward); the retained move is therefore not necessarily the best candidate. These source observations make repeated exploration plausible. They are not a separately reproduced proof of a specific cycle, and changing either rule would alter algorithmic search behavior. Neither was changed.
